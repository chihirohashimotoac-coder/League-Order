# Opponent-Aware Optimizer (対戦相手最適化)

プリセット `OPPONENT_OPTIMIZED` (表示名「対戦相手最適化」)。次戦の相手の出場予測に対して、
**推定 Match 勝率**が最も高くなるオーダーを探す。予測モデルは [`PREDICTION_MODEL.md`](./PREDICTION_MODEL.md)。

## 1. 入力

`OrderInput.opponent: OpponentContext` (任意)。SETUP で、キャッシュ済みの Match Intelligence と
選択したフォーマット・選手から作られ、オーダーと一緒に保存される (数 KB)。

- 自選手の予測強度 (PPR 点) と信頼度
- ゲームごとの相手サイド強度の分布 (和 1)・試合形式 (先取レッグ数・Cricket)・信頼度
- 相手名・試合 ID・日付・生成時刻

保存済みオーダーは `opponent` を持つため、ライブのキャッシュが無くても同じ数値で再評価できる。

## 2. 目的関数

既存の加法スコアに 1 項を加える (`src/optimizer/scoring/score.ts`):

```
Score = … 既存の各項 … + w_opponent · OpponentWin
OpponentWin = mean_g E[P_game(自サイド vs 相手分布)]      (= 期待勝ちゲーム数 / ゲーム数)
```

- Combo ごとに前計算 (`Combo.oppWin`)、分枝限定の上界は各ゲームの最大値の和 (他の項と同じ扱い)。
- 予測と最適化は**同じ関数** (`sideStrength` + `expectedGameWin`) を使うため、画面の推定勝率と
  最適化の内部値は一致する。
- 他のプリセットは `w_opponent = 0`。加算は厳密に `+0` で、**探索・数値とも従来と同一**
  (テスト: 相手データの有無で他プリセットの配置・総合値が変わらない)。

## 3. 重みとロバスト化

| 重み | strength | gameFit | pairFit | fairness | roleFairness | novelty | consecutive | season | opponentWin |
|---|---|---|---|---|---|---|---|---|---|
| 対戦相手最適化 | 0.3 | 0.45 | 0.35 | 0.9 | 0.3 | 0 | 0.5 | 0.05 | 2.4 |

- 公平性 (fairness / roleFairness / consecutive) は**バランスと同水準の Soft 項**として残す。
  推定勝率が置き換えるのは主に「生の戦力」項であり、公平性ではない。
  これにより「最強選手を全ゲームに出す」退化解を避ける (検証: 6 名 8 枠で出場差 ≤ 1、全員出場)。
  > 判断記録: 当初案 (fairness 0.3) では、ダブルス 1 枠の推定勝率 +0.6 が公平性の罰則を上回り、
  > 1 名が 4 回・3 名が 0 回という退化解になった (テストで検出)。バランス水準へ引き上げた。
- **信頼度による減衰**: `effective = base × factor` (HIGH 1.0 / MEDIUM 0.7 / LOW 0.35)。
  減らした分は strength に移す。不確かな予測に最適化全体を賭けない。
- **フォールバック**: 相手データが無い / どのゲームにも対応付けできない → 勝利優先の重みで生成し、
  警告「対戦データ不足のため…通常の勝利優先 (戦力重視) で生成しました」。

## 4. 最終順位 (Match 勝率での再評価)

Match 勝率はゲーム勝率の非線形関数 (Poisson-binomial) なので探索の加法スコアにはできない。
探索 (Beam → B&B → 局所探索) で得た完全解のプールのうち、
**加法スコアが最良から `RERANK_SCORE_TOLERANCE` (スコア幅の 1.5%) 以内**のものを
`riskValue = P(win) + ½P(draw)` で再評価して選ぶ。公平性は許容幅で担保される
(公平性を大きく犠牲にした解はプールに入らない)。

リスクモード (将来用、UI 未提供): `NEUTRAL` (既定) / `CONSERVATIVE` (P(負けない)) / `AGGRESSIVE` (P(win))。

### 4.1 偏りゲート (出場の偏りの採否。docs/DESIGN.md 追補 v1.5 W1)

再順位付けの後に、選ばれた案が**均等案より偏っていないか**を判定する (`optimizer/skewGate.ts`)。
相手があるときの推定利得は、**この `riskValue` と同じ Match 値**の均等案との差 (再順位付けと同じ定義)。
偏りの大きさ `steps` (1 試合ぶんの移動 = 1) に対し `利得 ≥ θ × steps² × c` (θ = 2pt、c = HIGH 1 / MEDIUM 1.5 / LOW 採用不可)
を満たさなければ均等案を使う。c の信頼度は**相手データの信頼度と、均等案と本数が違う自チーム選手の信頼度の最小**。
通った案はさらに、ゲートを通る一手ずつの山登りで**推定 Match 値**が上がる方向に局所改善する (公平性は偏りの
大きさに対する必要利得の形で入っている)。ゲートの判定・理由・画面の出場回数は同じ定義 (総出場と役割別の超過 SSD) を読む。
これにより、相手データの信頼度が低いときに「出場ゼロが 2 名」(2/2/0/0 など) になる案は採用されない。

## 5. 相手の不確実性

相手の最頻オーダー 1 本ではなく、**分布に対する期待値**を最大化する
(`E[P_game] = Σ q(lineup)·P(…)`)。テスト: 55% 弱い選手 / 45% エースの枠で、最頻値だけを相手にした場合より
推定ゲーム勝率が低く評価されること、相手のエースの位置が変わるとオーダーも変わること。

## 6. Hard 制約

新しい項は Soft のみ。候補生成・`canPlace`・局所探索の `hardFeasible`・最終の `validateHardConstraints`
はすべて従来どおり。再評価も `hardFeasible` を通った解だけを対象にする。

## 7. 候補比較と説明

対戦相手最適化を選ぶと 4 案: 対戦相手最適化 / 勝利優先 / バランス / 公平性優先。
相手データがある限り全候補に `prediction` (推定 Match 勝率・引分・期待勝ちゲーム・信頼度・ゲーム別) が付く。

結果画面:
- 候補カード: 推定勝率 (信頼度)・期待勝数
- 対戦相手パネル: 推定 Match 勝率、期待勝ちゲーム、**通常の勝利優先との差 (+N pt)**、
  主な理由 (勝利優先から推定勝率が上がったゲーム上位 3 件と相手の予想)、信頼度、独立近似の注記
- ゲームカード: 「推定 61% ・ 中」
- 詳細分析: ゲームごとの「推定ゲーム勝率」とその理由、全体の「推定 Match 勝率」

表現: 「推定」「参考値」を使い、「確実」「必勝」等は使わない。設定で推定値の表示を消せる。
共有画像・テキストには推定値を含めない (共有層は予測を参照しない)。

推定 Match 勝率が勝利優先の案より低い場合 (公平性を保った結果)、対戦相手パネルはその理由
(「出場バランス (公平性) を保つため…」) と、勝利優先の案を選べることを明記する。
スマートフォン幅では 4 案を 2 × 2 で並べる (横スクロールを出さない)。

## 8. Optimizer backtest (Phase 6)

`src/optimizer/orderBacktest.test.ts` / `npm run backtest` §3。

- **時間旅行リプレイ** (`src/test/n01/replay.ts`): 試合日 D の試合ごとに、フィクスチャのリーグを
  `today = D` で再生成する (シード付き・日付順に進むため、D より前の結果は同一で、D 以降は未実施になる)。
  実際の同期パイプライン (fetch → plan → intelligence → OpponentContext) を D 12:00 JST の時計で実行し、
  **その朝キャプテンが持っていたデータだけ**でオーダーを作る。参加者は実際に出場した選手。
  テストで「次戦 = その試合」「見えている今季 legs = D より前の試合の合計」を確認する (未来データ漏洩なし)。
- **比較するのはモデルの推定値どうし**: 推奨オーダーと実際のオーダーを、同じ試合前データ上の推定 Match 勝率
  (勝ち + ½ 引分) で比べる。実際の結果は反実仮想の正解にならない (別のオーダーなら何が起きたかは誰にも分からない)
  ため、「推奨なら勝っていた」とは言わない。

結果 (ATDO-like 今季 32 + TDO-like 8 = 40 チーム試合。**合成データ**であり実戦成績の改善を示すものではない):

| 指標 | 改修前 (main `cf63439`) | 改修後 (偏りゲート・F02/F03 込み) |
|---|---|---|
| 推奨 − 実際のオーダー (推定 Match 勝率、平均) | +1.54 pt | **+0.89 pt** |
| 最悪 | −2.30 pt | −3.61 pt (テストの許容は −5 pt) |
| 推奨が実際以上の試合 | 75.0% (30 / 40) | 67.5% (27 / 40) |
| 推奨 − 勝利優先候補 (平均) | +0.22 pt | +0.18 pt |
| 推奨の平均出場差 / 最多出場 | 0.70 / 2.50 | 0.70 / 2.50 |
| 勝利優先候補の平均出場差 / 出場差 ≥ 2 の試合 | 1.13 / 35.0% | 0.60 / 7.5% |
| 実際のオーダーの推定値 vs 実結果 (Brier) | 0.2081 (50%: 0.2500、n = 40、両チーム視点・小標本) | 同左 |
| Hard 制約違反 | 0 | 0 |

出場の偏りを抑える代わりに、推定 Match 勝率は平均で約 0.6pt 下がる (これは設計上のトレードオフで、悪化として明記する)。
`npm run backtest` §3c に、ゲートの閾値ごとの同じ比較表がある。

## 9. 感度 (Phase 6)

ATDO-like の 7 ゲーム形式 6 試合で、定数を少し動かして再最適化する。
**regret** = 変更後のモデルで見て、新しい最良案が元の案より何 pt 良いか (小さいほど元の案で困らない)。
k の変更は「全強度のリーグ平均からの距離を s 倍」で厳密に再現する (`P_leg = logistic(k·Δ)` のため同値)。
信頼度の閾値を少し動かすと水準は最大 1 段動くので、1 段上下させる (最悪側)。

| 変更 | 平均 regret | 最大 regret | 席の入替 |
|---|---:|---:|---:|
| recency 1 / 0.8 / 0.6 | 0.16 pt | 0.98 pt | 12.5% |
| recency 1 / 0.4 / 0.2 | 0.55 pt | 3.30 pt | 18.1% |
| shrinkage prior 20 legs | 0.15 pt | 0.93 pt | 5.6% |
| shrinkage prior 45 legs | 0.00 pt | 0.00 pt | 11.1% |
| logistic k × 0.8 | 0.00 pt | 0.00 pt | 11.1% |
| logistic k × 1.2 | 0.15 pt | 0.88 pt | 5.6% |
| 信頼度 1 段下げ | 0.62 pt | 3.75 pt | 18.1% |
| 信頼度 1 段上げ | 0.13 pt | 0.77 pt | 15.3% |

席の入替は 6〜18% 起きるが、元の案の推定勝率の損失は平均 1 pt 未満・最大 4 pt 未満 —
入れ替わるのはほぼ同等な選択肢どうしである。テストの許容: 平均 < 2 pt、最大 < 6 pt、入替 < 50%。

再現性: アプリの探索は時間上限で止まるため、上限に達した探索の結果は端末の速さで変わりうる。
`npm run backtest` は探索をノード数上限だけで打ち切る (時計を使わない) ので、どの環境でも同じ数値になる
(上の表と §8 はこの条件の値。所要時間の §4 だけはアプリと同じ設定で計測)。
単体テスト (`orderBacktest.test.ts`) はアプリと同じ時間上限で回すため値は多少揺れるが、許容値には十分な余裕がある。

## 10. 限界

- 推定勝率は合成データでしか検証していない (PREDICTION_MODEL.md §9)。実リーグでの較正後に
  `CONFIDENCE_WEIGHT_FACTOR` と `opponentWin` の重みを見直す余地がある。
- 公平性を Soft 項として残すため、対戦相手最適化の案は勝利優先の案より推定勝率が低いことがある
  (リプレイ 40 試合中 平均 +0.22 pt、個別には −3.7 pt の例あり)。画面でその旨を示す。
- 時間上限で探索が打ち切られた場合 (`NOT_EXHAUSTIVE`)、同じ入力でも端末の速さで結果が変わりうる。
