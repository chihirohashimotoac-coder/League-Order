# Throw-Order Model (投順モデル)

Doubles / Trios / Gallon (4 人以上) の **投順 (1投目, 2投目, …)** を、メンバーの組合せとは別の戦術として扱う
モデルの仕様。予測の土台は [`PREDICTION_MODEL.md`](./PREDICTION_MODEL.md)、探索は
[`OPPONENT_OPTIMIZER.md`](./OPPONENT_OPTIMIZER.md)、格上対策案は [`UNDERDOG_PLAN.md`](./UNDERDOG_PLAN.md)。

モデル版: `throw-order-v1` (`THROW_ORDER_MODEL_VERSION`)。すべての定数は **暫定の事前値** であり、実測で
校正した値ではない (§8, §11)。

## 1. 変更前の挙動と問題 (開始 commit `06e709d`)

| 項目 | 変更前 | 問題 |
|---|---|---|
| 出場者の並び | `prepare.ts` が出場者を **内部 ID 順** に並べ、組合せ (combo) はその添字順。`materialise` はロック以外をその順で書き出す | 複数人ゲームの「1 人目 / 2 人目」が内部 ID 順 = 登録順。ID が入れ替わるだけで書かれる順番が変わる |
| 推定 | ダブルス以上は各メンバー強度の平均 (+ ペア相性)。順番は推定に入らない | 同じメンバーを別の順で投げても推定が同じ。順番を比較できない |
| 候補の同一性 | 署名・重複排除はメンバー集合 | 同じメンバーの別順は別候補として扱われない |
| 相手のオーダー | Position model が組合せをソートして保持 (`[...playerKeys].sort()`) | 相手の投順の傾向が失われる |
| 役割別の強さ | 全ゲーム共通の強度 (PPR / Rating / 履歴補正) | Singles 型・Doubles 型・01 / Cricket の差を扱えない |
| 画面 | `PLAYER 1` / `PLAYER 2` | 投げる順だと読めない |

## 2. 01 のレース (`raceModel.ts`)

01 の 1 レッグは「各サイドが 0 点に到達するまでの訪問 (visit = 3 投) 数」の競争。複数人のサイドは登録した
順に 1 訪問ずつ交代で投げる (m(v) = v 回目の訪問の投げ手 = `members[(v − 1) mod k]`)。

```
得点区間   S_j = Σ_{v≤j} X_{m(v)},  X_m ~ N(μ_m, σ(μ_m)²)        (正規近似)
           P(J ≤ j) = 1 − Φ((need − Σμ) / √Σσ²),  need = start − FINISH_ZONE
上がり区間 J + 1 回目以降、投げ手 m が 1 訪問で上がる確率 f_m
訪問数     P(T = t) = Σ_j P(J = j) · Π_{J<u<t} (1 − f_{m(u)}) · f_{m(t)}
レッグ     P(先攻で勝つ) = Σ_t P(T_A = t) · P(T_B ≥ t)
           P(後攻で勝つ) = Σ_t P(T_A = t) · P(T_B > t)       → 平均 (先攻は事前に分からない)
```

- 定数: `FINISH_ZONE` 60 点、`σ(μ) = 10 + 0.35 μ`、訪問の打ち切り `ceil(need / 18) + 40` (上限 200)。
  打ち切り後の質量は両者未了として 1/2。
- 閉形式 + 1 回の畳み込み。**乱数・モンテカルロは使わない** (シード不要、完全に決定的)。
  分布はサイド (メンバー順, 開始点数) ごとにキャッシュし、キャッシュは値を変えない (テストで検証)。
- 両サイドは独立 (01 はボードを共有しない)。

### 2.1 推定への組み込み (`throwOrder.ts`)

全体の強さの差は、これまでどおり校正済みのロジスティック (`matchup.ts`) から来る。レースモデルは
**順番が変える分だけ** を PPR 換算で足す:

```
L(o, t) = logit P_race(自軍を順 o、相手を順 t)       ō, t̄ = 各サイドを平均的なメンバーに置き換えたもの
effect  = (L(o, t) − mean_{o'} L(o', t̄) − mean_{t'} L(ō, t') + L(ō, t̄)) / slope
slope   = d logit P_race / d PPR  (平均化したサイドで ±1 PPR の数値微分)
P_game  = race_m( logistic(k · (side mean + ペア相性 − 相手 + effect)) ),  |effect| ≤ 4 PPR
```

- 2 つの平均 (自軍の全順・相手の全順) を引くので、**メンバーの構成がどの順でも生む差** (速い上がりの
  選手がいる等) は投順の効果に含めない。自軍の全順で平均すると effect は 0 = 投順だけの効果。
- 相手側の投順も effect に入る (自分の並びが上げ、相手の並びが下げる)。相手サイドの分布全体で期待値を取る (§5)。
- Singles には順番が無く、Cricket と 5 人以上のサイドはモデル化しない (共有ボード・PPR との関連が弱い /
  順列が大きすぎる)。どれも推定は順番なしの値と **完全に同じ** で、投順は常に強い順。
  Singles でも強さは **役割別強度** を使い、最適化と画面は同じ数値になる。
- 開始点数: n01 の `startScore`。無ければ 501 (1–2 人) / 701 (3 人) / 1001 (4 人以上) と推測し、
  その旨を画面に出し、投順判断の信頼度を 1 段下げる。

## 3. 上がり (finish) の推定 (`finishing.ts`)

n01 の公開成績には **チェックアウト率がない** (ダブルの試投数・上がりの試行数が無い)。PPR から精密な
チェックアウト率は作らない。保守的な事前値と、n01 が実際に持つ情報による弱い補正だけを使う:

```
prior(μ) = clamp(0.30 + 0.004 (μ − 50), 0.15, 0.50)   (Steel、double-out)
         = clamp(0.40 + 0.004 (μ − 50), 0.20, 0.60)   (Soft)
rate     = clamp(prior · exp(−0.08 · excess), 0.08, 0.70)
excess   = (First9 − PPR − リーグの通常差) · legs / (legs + 30)    (縮約済み、playerStrength.ts)
```

- First 9 が全体平均よりリーグの通常差以上に高い = 序盤の得点に比べて終盤 (上がり) で多くのダーツを使う、
  という **弱い証拠** として扱う。信頼度はその選手のレッグ数の信頼度。
- High Out / Best Leg は単発の極値 (レッグ数で伸びる) なので使わない。
- 証拠が無ければ事前値のまま (`source: 'prior'`)。事前値だけでは投順の採用条件「投順データあり」(§6) を満たさない。

## 4. 役割別の強さ (`roleStrength.ts`, `roleHistory.ts`)

```
役割別強度 = 基本強度 (履歴補正 PPR。従来どおり) + Δ(役割)
役割      = 構造 (Singles / Doubles / Trios / Gallon-Team) × 種別 (01 / Cricket)
```

Δ の推定順位 (各段は次の段へ縮約。`(W · 平均 + K · 親) / (W + K)`、K = 30 レッグ、Cricket は 2 倍):

| 順位 | データ | `source` |
|---|---|---|
| 1 | n01 で **試合前に** 同じ役割で投げた成績 | `n01-role` |
| 2 | 同じ種別の近い役割 (Doubles ↔ Trios ↔ Gallon。Singles は近い役割に含めない) | `n01-near` |
| 3 | キャプテンが入力したゲーム適性 (1–5、3 = 中立、1 段 = 1 PPR) | `aptitude` |
| 4 | 何も無い: Δ = 0、基本強度そのもの (リーグ平均補完は従来どおり) | `base` |

- 1 ゲームの証拠 (`roleHistory.ts`、PPR 換算):
  - 01: `サイドのそのゲームの PPR (3 × 得点 / ダーツ) − メンバーのその Season の PPR 平均`。
  - Cricket: 結果の残差 `(勝敗 − p̂) / (0.09 · max(0.05, p̂(1 − p̂)))`、±15 で打ち切り、重みは 01 の 0.1 倍。
    p̂ は自サイドと **相手サイド** の Season PPR 平均 (不明ならリーグ平均) からの期待勝率 (相手の強さを考慮)。
- 重み = recency (Season 重み) × レッグ数 / k。**k 人ゲームは各メンバーに 1/k** (チーム成績を全員に満額付けない)。
- **生の勝率を強さとして使わない** (Cricket の結果も期待値 p̂ からの残差のみ)。
- 試合日以降のゲームは捨てる (未来データ漏れなし。件数は `droppedFuture`)。Season PPR が不明なメンバーの
  ゲームは何も言わない (0 にしない)。|Δ| ≤ 8 PPR。
- 信頼度: 同役割の重み付きレッグで 40 / 12 (選手データと同じ閾値)、近い役割は 1 段下げ、適性だけは LOW、
  Cricket はさらに 1 段下げ。選手データの信頼度より高くはならない。これは **役割補正の根拠** の信頼度で、
  説明に表示する。予測と投順判断に使う選手の信頼度は選手データの信頼度のまま (役割補正は縮約・上限付きの
  小さな補正なので、根拠が薄くても選手の推定を不確かにはしない。適性を入力しただけで「参考値」にはならない)。
- 出典データ: n01 `match/list` (§4.1)。取得できなければ近い役割・適性・基本強度に順に戻る。
- 各メンバーの根拠 (`source`、同役割のゲーム数・レッグ、近い役割のゲーム数、適性) はオーダー内に保存し、
  画面の「強い順の根拠」に出す。

### 4.1 n01 `match/list` (役割の証拠)

- `GET match/list?tdid=…&tmid__regex=_<tpid>&count=100[&skip=…]` — そのチームが出た試合の
  ゲーム記録 (ゲームごとの `statsData`: 順番付きのメンバー、獲得レッグ、得点、ダーツ数、`startTime`)。
- `tmid__regex` は **正規表現ではなく文字列の部分一致** として扱われる (2026-10-12 に実 API で確認:
  `_X6iU` は一致、`_X6iU$` / `_X6iU(_|$)` / `_X6i.` は 0 件)。そのため `_<tpid>` を送り、受け取った行は
  どちらかのサイドがそのチームのゲームだけを使う (長い tpid の前方一致などで混ざる他チームの行を除く)。
- 応答の形 (`statsData[2]`、`tpid`、`order[]`、`winLegs`、`allScore`、`allDarts`、`allMarks`) と `count` / `skip`
  も実 API で確認済み。
- 1 ページ 100 行、満杯のときだけ次ページ、最大 3 ページ (満杯の判定は n01 が返した行数。読めない行があっても
  次を読む)。2 ページ目以降がすべて読めない行なら、そこで止めて読めた分を使う。今季と過去 Season、自チームと相手。
- **任意の取得**: 失敗しても同期は続行し、証拠が薄くなるだけ (`notes` には出さず役割の `source` に表れる)。
- 同期 1 回の GET: 16 → **22** (`match/list` が自チーム・相手 × 3 Season)。フィクスチャで重複 0
  (`n01Requests.test.ts`)。
- 実 n01 での CORS (ブラウザから直接) は **未確認** (サーバ間の読み取りでは確認済み)。公開後のスモークテスト
  (`Smoke test the published site`) で、ブラウザからの全 n01 応答が 200 で読めることを確認する。

## 5. 相手の投順の分布 (`positionModel.ts`, `opponentContext.ts`)

- `team/order/list` の `order[]` は登録順 = 投順。**ソートせずに保持** (`orderedLineups`)。投順が無い応答を
  「投順が分かっている」とは扱わない。
- 先頭傾向 `score` (1 = 常に 1 投目、0 = 常に最後、0.5 = 傾向なし): 構造 (Doubles 等) の観測 → チームの全多人数
  ゲーム → 0.5 へ縮約。
- 相手サイドの分布 (version 2 のコンテキスト):
  - 観測された組合せは登録順のまま (重み α = 観測 / (観測 + 3))。
  - モデル化した組合せ (1 − α) は Plackett–Luce: `λ = exp(4 · (score − 0.5))`。
    チームに投順の観測が無ければ **全順を同等** (`known: false`)。
  - 各メンバーはそのゲームの役割での強さと上がり推定を持つ。強度 3 桁・上がり 4 桁で丸め。
  - サイドは最大 24。それを超えると確率の高い 23 件を残し、残りは **1 つの残余サイドに畳み込む**
    (確率の合計と、投順の各位置の確率加重平均の強さ・上がりを保つ)。捨てて再正規化はしない。
  - 投順を扱うのは 4 人まで (`MAX_ORDERED_MEMBERS`)。5 人以上の Team / Gallon は version 1 と同じ順番なしの
    サイドで持つ (投順の推定はしない。順列の展開は 8 人で 1 組合せあたり 40 320 通りになるため)。
- 推定は **分布全体の期待値** (最も多い 1 通りではない)。
- `order.known` = チームに投順の観測があり、先頭傾向がある。`order.confidence` は投順観測量 (slot 閾値 6 / 2.5)。
- 画面: 「相手の 1 投目の予想: X 62% / Y 30% (投順の観測 4.0 回分)」、無ければ
  「相手の投順は過去データから推定できません (全順を同等と仮定)」。
- version 1 のコンテキスト (以前の保存オーダー) はメンバーを持たず、従来どおり読む。

## 6. 投順の決定 (`optimizer/throwOrder.ts`, `decideThrowOrder`)

探索は **誰が出るか** (メンバー集合) を選び、各集合の投順はここで 1 つの規則で決める:

1. ロックされた枠 (`n 投目`) はその選手のまま。
2. 残りは **強い順**: そのゲームの役割別強度 → 基本強度 → Rating → PPR → 名前 (正規化)。内容だけで並べる。
   内部 ID は「全データが同一の 2 人」の最後の区別にだけ使う (戦術上どちらが先でも同じ)。
   → ID だけを入れ替えても投順は変わらない (テスト + backtest 5b で 240/240 件確認)。
3. 相手データと投順モデルがあるとき、ロックが許す **全順列** (4 人まで: 2! / 3! / 4! = 2 / 6 / 24 通り) を推定し、
   強い順以外は次の **すべて** を満たすときだけ採用する:

| 判定順 | 条件 (満たさなければ強い順) | `fallback` |
|---|---|---|
| 1 | 最良の順の推定ゲーム勝率 − 強い順 ≥ **2pt** (ちょうど 2pt は採用。浮動小数の許容 1e-9) | `small-gain` |
| 2 | 判断の信頼度が **MEDIUM 以上** (相手ゲームと各メンバーの選手データの最小。開始点数が推測なら 1 段下げ) | `low-confidence` |
| 3 | 少なくとも 1 人に投順の証拠 (First 9 由来の上がり推定、信頼度 MEDIUM 以上) がある | `no-order-data` |
| 4 | 相手の投順が分かっている (`known` かつ信頼度 MEDIUM 以上) | `opponent-order-unknown` |
| 5 | 安定: 上がり証拠を半分にしても、訪問ごとのばらつきを ×1.25 / ×0.8 にしても、強い順より良い | `unstable` |

- 同点は強い順、次に強い順に近い順 (強い順での順位の辞書順)。**ID には決して落ちない。**
- Cricket と 5 人以上は常に強い順 (`cricket` / `large-side`)。相手データが無い・旧モデルのオーダーも強い順。
- 投順はそのゲームの推定だけを変える。公平性・役割・連続・Hard 制約の項は集合で決まるので、集合ごとに
  投順を決めても探索の他の項は変わらない。各ゲームの勝率を最大化すれば Match の目的 (勝率・P(W≥1)・E[W]) も
  単調に上がる。
- 探索との統合: 組合せの署名・重複排除・タイブレーク・Beam・DFS・polish・rerank は **順番込み**。
  順番の推定はメンバー集合ごとにメモ化 (`orderMemo`) し、推定値もキャッシュ。Hard 制約は迂回しない
  (最終解は `validateHardConstraints` で再検証)。
- 手動の並べ替え: その順のまま推定し、ゲーム勝率と Match 勝率を即時再計算する。**ルールが選ぶ順と違うときだけ**
  手動 (`adopted: 'manual'`) と表示する (別のゲームを編集して再評価しても、触っていないゲームは手動にならない)。
  手動で強い順に戻したときは「手動で強い順に変更」と、推定で選ばれていた順の差を表示する。
- 以前のオーダー (`throwOrderModel` なし) には投順の記録・説明を付けない (従来どおりの表示)。
- 「ゲーム別の理由」に並ぶ選手も投順 (1投目から) で表示する。

### 6.1 Singles とエース (`aceMatchup.ts`)

「相手エースに自エースを必ず当てる」固定ルールは無い。Match 全体の推定勝率で配置し、相手エース枠を
自エースが受けていない場合は、エースを当てた並びとの比較 (推定 Match 勝率の差) を表示する。

## 7. 画面での説明方針

- 枠のラベルは `1投目` / `2投目` … (`PLAYER n` は廃止)。Singles は `選手`。選択欄の読み上げは
  「Game 2 Doubles 501 の1投目」。
- 各ゲームの下に 1 行: `投順: 強い順 (このゲームの役割別強度の高い順)` /
  `投順: 推定勝率で選択 (強い順より +2.3pt)` / `投順: 手動で変更` / `投順: 手動で強い順に変更`。
  強い順と違うとき・手動のときだけ強調表示。
- 強い順以外を採用したとき: **通常の順 (強い順)・変更理由・推定改善幅 (強い順 → 採用順の推定ゲーム勝率)・
  信頼度・利用した相手の投順傾向** を表示。
- 強い順を維持したとき: 理由 (§6 の表の文言。2pt 未満なら最大の差も) を表示。
- 役割別強度: 各メンバーのそのゲームでの強さ (PPR 換算)・役割補正・根拠 (`n01 の同じ役割の成績 N試合` /
  `n01 の近い役割の成績 (縮約)` / `ゲーム適性の入力` / `総合の強さ (役割別データなし)`)・信頼度。
- 並べ替えはドラッグ不要の **ボタン** (`1投目 ⇄ 2投目`、高さ 44px = `--tap-target`、
  `aria-label` 「Game 2 Doubles 501: 1投目と2投目を入れ替え」)。ロック中・空席では無効。
  プルダウンでの選手変更・ロック・Undo / Redo・ゲームごとの再計算・再最適化は従来どおり。
- 断定表現 (確実・必勝) は使わない。すべて「推定」。
- 360px 幅で横スクロールなし (Playwright + 目視で確認、§8 の E2E)。

## 8. Backtest (`npm run backtest` の 5 / 5b、`scripts/backtest.baseline.md`)

**すべてモデルの推定値。** フィクスチャ (シミュレーション) と架空チームのデータであり、実戦の勝率改善を
示すものではない。

## 9. 保存と互換

- 新しいオーダーの入力に `throwOrderModel: 'throw-order-v1'` と `roleStrength` (使った役割の証拠) を保存。
  解には `throwOrder` (ゲームごとの投順・強い順・採用理由・推定・信頼度・相手傾向・根拠)。
- 保存済みの再評価は保存した入力だけで行う (同じ推定が再現される)。
- **以前のオーダー** (`throwOrderModel` なし): 読み込み・表示・共有・編集はそのまま。**自動で再計算しない。**
  推定は従来の順番なしのモデル。保存順は変えない。マイグレーションは読み込み時の解釈だけ (保存データは書き換えない)。
- 保存順 = 投順。共有テキスト・画像・差分・fingerprint はその順。投順だけの変更でも fingerprint が変わり、
  確定済みは「変更あり」になる。
- ID の付け替えで投順は変わらない (§6)。
- テスト: `src/storage/throwOrderCompat.test.ts`。

## 11. 限界

- 定数 (FINISH_ZONE、σ、上がり事前値、弾性 0.08、2pt、効果の上限 4 PPR) は暫定値。実測データで未校正。
- n01 にはチェックアウト率が無く、上がりは First 9 からの弱い推定。現実的なデータでは強い順以外はほぼ採用されない。
- 01 のレースは正規近似と「上がり区間で毎訪問一定確率」の単純化。バスト・残り点数・ダブルの選択はモデル化しない。
- Cricket の投順はモデル化しない (常に強い順)。
- 相手の当日の戦術 (投順の変更・欠場) は過去データからは分からない。分布は過去の傾向に過ぎない。
- `match/list` のブラウザからの CORS は公開後のスモークテストで確認する (サーバ間の応答形・絞り込み・ページングは実 API で確認済み)。
- 01 の役割の証拠はそのゲームの PPR 残差で、相手の強さでは補正していない (PPR は得点率で、相手への依存は
  小さいという仮定)。Cricket の証拠だけが相手の Season PPR を使う。
